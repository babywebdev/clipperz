# Bundled Self-audit Procedure

Adapted from the standalone `.agents/skills/feature-audit/SKILL.md` as source material. This installed procedure is self-contained and does not activate that skill or require its sibling skills. Contract authority, verification and conditional closure govern all actions.

## Audit method

Select the actual implementation snapshot and changed paths using Git or content manifests; include relevant dependencies and changed inputs. If the diff does not capture the session, reconstruct from available evidence and state the limit. Scope correctness to affected behavior and risk. A substantial cycle uses the README-configured self-audit template; a small reversible task may use a concise result. The audit is findings-only: inspect and run authorized side-effect-bounded checks, but do not edit implementation during the audit pass. Returning to an already-authorized implement/repair activity needs no repeated approval. Record actual target, evidence and remaining uncertainty; do not manufacture findings.

First sweep changed work for unused imports, dead or commented-out code, duplicate logic, orphaned files, debug leftovers and unnecessary complexity. A single-use abstraction is a finding only when it adds unnecessary complexity in its actual context. Distinguish clearly safe cleanup from choices requiring a design decision; do not delete during this audit pass.

In the same sweep, look for a weakened bar: new suppression comments (`@ts-ignore`, `@ts-nocheck`, `eslint-disable`, `biome-ignore`, `istanbul ignore`, `# noqa`, `# type: ignore`); skipped or deleted tests, and assertions removed from tests that remain; throwing stubs, empty `catch` blocks and TODOs standing in for an implementation; lowered thresholds or disabled checks in configuration, such as `typescript.ignoreBuildErrors` in a Next.js config, loosened `tsconfig` strictness or removed CI steps. Classify each as a weakened bar or as justified, with evidence, and disposition it like any other finding; the check never blocks automatically. When available, `python docs/workflow/scripts/bar-guard.py --base [baseline]` lists candidates; its output is a lead, not a verdict, and it skips Markdown and workflow records.

Assess each of eleven lenses. Give a concise N/A with reason when a lens does not apply; depth follows risk. A concrete finding states trigger, impact, location and snapshot, evidence or unverified status, uncertainty and required outcome. Severity reflects real production consequence, not an API name or fixed threshold. For cheap, safe discriminating checks, run them and record results; otherwise mark the limit. Use available current authoritative evidence for dependency advisories; without it, say not assessed, never safe by default.

1. **Critical correctness:** trace a plausible high-impact trigger through callers and effects, including data loss, races, null paths, leaks and loops. Do not assert a bug from a pattern alone.
2. **Security attack paths:** identify the actor, controlled input, path to a dangerous sink, missing protection and production impact. Assess injection, access control and ownership, path/URL/deserialization hazards, auth/crypto, secrets, validation, output encoding and affected CI/container/IaC boundaries as applicable. An unsafe-looking API alone is not proof.
3. **Test coverage:** find meaningful untested acceptance, regression, parsing, concurrency, permission or failure behavior. Name the outcome a test should prove and why existing coverage is inadequate; avoid mirror tests.
4. **Dependencies and supply chain:** inspect added/changed dependency versions, lock/pin state, callers, current advisories when available, install scripts and mutable assets. Record uncertainty when current advisory data is unavailable.
5. **Failure paths:** trace partial failures, cleanup, resource release, swallowed errors, timeouts/retries and fail-closed security paths to concrete consequences.
6. **Breaking changes and migrations:** inspect API/schema/config consumers, persisted data, backfill and deployment order; verify compatibility or state a concrete break.
7. **Documentation drift:** compare observable behavior, public contracts and setup to affected docs; skip purely internal non-observable changes.
8. **Accessibility:** for UI changes inspect semantics, keyboard/focus, names/alt text, contrast and focus visibility; otherwise N/A.
9. **Observability:** assess whether new failure paths carry actionable, secret-free diagnostics; a silent failure needs a concrete trigger.
10. **Engineering invariants:** compare changed behavior to actual project protections for sensitive data, permission scope, cross-surface consistency and external side-effect controls. Use sufficient code/evidence references; mark inconclusive rather than assert drift without support.
11. **Performance and resource bounds:** look for N+1 queries, unbounded reads and missing pagination, synchronous work in request paths, serverless connection-pool exhaustion and in-memory rate limiters that do not hold across instances. A performance claim needs the same measurement before and after, with the environment named.

List uncertain assumptions and investigate material ones through actual code paths or bounded checks until resolved or a specific remaining proof is named. Name the largest plausible blind spot. Do not convert absent evidence into reassurance. Summarize cleanup, every lens, confidence investigation, blind spot, and verdict: `PASS` for complete applicable assessment with no findings; `PASS-WITH-FINDINGS` only for explicitly disposed nonblocking items; `BLOCKED` for a confirmed blocker; `INCOMPLETE` for material unavailable assessment/evidence. A blocking/incomplete required audit prevents acceptance. Self-audit never substitutes for runtime verification or fresh initial review. Describe a needed capability or focused check directly; no required sibling skill, automatic plan file or blanket approval per finding.
