# Common Project Process

The contract controls authority and evidence. This file describes activities. Read `docs/workflow/README.md` for the installed paths, heading map, selected references, grants, storage and existing state owners. Follow the natural assignment; activity headings are not roles or permissions. The Status lane decides which fresh session performs each activity, and rights move only by handoff (contract Review procedure). Read complete applicable contract Part B sections before action.

## Orient

Read README configuration, contract Part A, this section and applicable activity sections, shared facts and standing protections, selected applicable references, task Status or established phase owner, then a bounded metadata index. Read whole applicable reference requirements and the relevant ADR and external-record sections before affected design, implementation or review. Read `docs/workflow/record-frontmatter.md` before writing or reconciling record metadata, including through the direct-read fallback. Use installed read-only helpers when available; without Python use bounded direct sections/headers. Metadata and summaries route reads, not authority. Historical, stale or unclassified records and unresolved findings remain discoverable when relevant. Open requirements, criteria, constraints, baseline and exceptions before implementation. Do not orient from whole report folders, backups, transcripts or archive-dnr. Section-first logical reads around 2,000–4,000 output tokens are a soft guide; larger reads need a named reason. Do not reread unchanged reliable context.

## Plan

Determine authorized outcome, risk, protected boundaries and do-not-build scope. Reassess installed reference applicability at the start of substantial work and when task capabilities change, record the selected applicable references and relative supporting dependencies in README, and surface missing coverage without silently adding a service or reference. Retain user customizations and removed selections unless an authorized decision changes them. Before detailed planning compare actual code, schema/interfaces, config, relevant ignored inputs, predecessor results, unresolved findings and assumptions with the baseline. Remove satisfied work; keep later partitions provisional. Record current baseline and approved exceptions in spec head, changes in append-only spec log. Define the observable implementation completion condition. For open-ended investigation name the evidence or lack of progress that prompts reassessment; add a cap only when explicitly agreed. A kickoff conversation need not recur for each slice. Unrelated HEAD drift alone does not invalidate a plan. For substantial work define behavioral slices, failure behavior, prerequisites and one acceptance-to-check map. Include applicable generic safeguards: trust-boundary validation, server-side permissions, data isolation, compatibility with existing data/callers, safe retry behavior and surfaced failures, even with no selected reference. For auth, payments, customer data, migrations or security classify unassigned risk at least contained and state why. Record the lane in Status `Lane:` from that classification; Isaac may assign a lane, and phase work follows the lane its risk warrants. Verify changing external technical/legal requirements against current authoritative sources before affected design, recording source/date/uncertainty. For material decisions record current decision, alternative, evidence, tradeoff, owner, affected criteria and resolution; keep independent work moving. Consequential unsettled design requiring independent judgment gets focused fresh assessment before expensive/irreversible action. For installed phase work, supply project-specific direction and prerequisites and the actual phase trigger under the selected reference; when that reference identifies a user-invoked skill, Isaac invokes it. Do not duplicate or replace its procedure/state owner. In the four-session lane the planner obtains Isaac's required approvals in its own session, then writes the implementation handoff (Communicate), which transfers task ownership and writing rights to a fresh implementer, and stops. In the small and contained lanes the planning session normally implements.

## Implement

Before writes, apply contract Plan freshness, Assignment and ownership, and Engineering defaults: reconcile the baseline, writer and checkout, including any ended-owner checkpoint; isolate authorized parallel work. Create pending receipt rows before substantial edits. Build behavioral slices and tests for acceptance or regression gaps; keep cleanup in scope. Optional fresh read-only exploration receives a named question and explicit paths/boundaries, and returns locations and about 600 words plus paths. It permits no writes, side effects, chaining or further delegation; the writer retains ownership and report authorship. Without suitable subagents, explore directly. Apply Recurrence and recovery for STUCK and its bounded diagnosis.

The implementer holds both rights. Decide and record implementation choices within delegated authority (Scope and design changes); ask Isaac directly about product, scope, cost or designated approvals, preserving unresolved requests for the next task owner. Never route back to the planner or wait on the reviewer. Record choices and limitations in the report. Before review handoff or contained closure, complete relevant project checks (typecheck, lint, build, tests), the receipt, self-audit, supported fixes and required pre-handoff check. Environmental, access and pre-existing failures remain `incomplete` or `fail`: resolve them, apply STUCK or ask Isaac; identify remaining blockers in the handoff. Small work and contained work needing no review complete here.

Pre-handoff check: first read the complete contract Review procedure, including Review lanes; it supplies the trigger, continuation exemption and check/confirmation caps. After self-audit and your fixes, spawn one fresh subagent, preferably without editing tools; record its type. Its brief, under about 400 words, gives facts and paths only, no reasoning or verdict: task, spec path/revision, lane; snapshot (base commit and diff command, or saved patch and manifest); receipt, evidence and selected references; a risk-chosen angle (default: correctness, failure paths and evidence against spec/criteria; security-floor work adds permissions, isolation and secrets). Instruct it: start from spec, diff and evidence before author reports; run no check, test, build, install, dev server or deploy, naming doubtful results instead; edit and spawn nothing; stay within about 30 tool calls or state why; return every finding in the review template's shape, separating confirmed findings, hypotheses and suggestions, in about 600 words plus paths, longer lists in full. Save brief and full return verbatim under `[evidence root]/pre-handoff-check/`; run named checks into the receipt. Use the report template's linked disposition index; do not duplicate the return.

Contained lane: for agreed local fixes, repair, rerun affected checks and write a concise post-repair self-audit of the delta across the eleven lenses, reusing unaffected coverage with a stated basis; then give a fresh confirmation subagent the check brief's instructions, each finding's original text and required outcome quoted from the saved return (no dispositions; quotes outside the word limit), the delta, new snapshot and affected receipt rows; it confirms each repair and reports problems the delta introduces. A rejected repair or new finding repeats this within the cap; then accept under Complete. Substantial and consequential lanes: repair agreed local findings, rerun affected checks and record disputed ones with evidence. A context warning or the implementer context threshold ends repairs in either lane: record the findings and hand off.

Write the review handoff and stop: task ownership, not writing rights, to a fresh reviewer-owner in the four-session lane; both rights to a fresh review-and-fix session for contained work. List your report and check as author-commissioned records, with proposed ledger rows.

## Verify

Apply contract Verification and evidence and Bind evidence: independent expectations, real behavior including failure paths, exact commands/results, secret-free artifacts, snapshot and executor. Existing adequate checks suffice; add tests for gaps. Preserve environmental/product distinctions, inaccessible evidence as incomplete, and historical limits. Delegation needs the enabled README flag and named checks, target, allowed effects, fixture owner/cleanup, evidence destination, snapshot and stop; validate executor/artifacts/binding and serialize shared state. For human assistance, prepare safe state within client-data/security bounds, give steps/expectations, distinguish observation from user report, capture text or original visuals as appropriate, index evidence and own cleanup. Never route prohibited actions through Isaac or await retry exhaustion. New/changed behavioral tests must fail on the baseline or reverted change before passing; record both results or infeasibility in the receipt. Unchanged-behavior refactor tests are exempt and should pass on both. Side-effecting checks use test-mode or non-production targets unless the assignment names production.

## Self-audit

After substantial implementation, audit the selected snapshot and relevant dependencies using the README-configured self-audit procedure and self-audit template; write the self-audit report. The audit pass produces findings, not fixes. Its verdict is additional evidence, not runtime proof or independent review. A blocking/incomplete required audit prevents acceptance. Before any handoff the author fixes its own supported in-scope findings without asking again, then refreshes affected checks and audit on the new snapshot; unresolved findings go in the report and handoff. Small reversible work may record a concise audit result in its ordinary result.

## Review

The Status lane decides who reviews and what it may write (contract Review procedure). Stabilize the implementation during review and confirm the actual snapshot and records are accessible; another checkout may lack uncommitted work. Start with the spec, actual diff/change inventory and required evidence, before author justifications, self-audit conclusions and any pre-handoff check. Expand into unchanged callers, dependencies, contracts, config and tests for concrete correctness/compatibility questions; record material limits. Inspect actual code and challenge flawed requirements. Include a weakened-bar pass over the diff: new suppressions, skipped, focused or deleted tests, removed assertions, throwing stubs, empty catch blocks, TODOs standing in for implementation, and lowered thresholds or disabled checks. When available, `python docs/workflow/scripts/bar-guard.py --base [baseline]` lists candidates as leads to dispose, not verdicts. Distinguish confirmed findings, hypotheses and optional suggestions; record trigger, impact, location/snapshot, evidence and required outcome. Compare ledger Open and class matches in Closed/archive, never archive-dnr. Keep required review pending until an accessible assessment exists; a recommendation alone does not update Status.

Reviewer-owner, four-session lane: review through two or three fresh read-only subagents, each on a distinct angle chosen by risk, such as spec compliance and correctness; tests and evidence; security, data and compatibility. Give each a neutral assignment: task/spec path, contract and process paths, selected references, relevant decisions, exact revision and reproducible snapshot, evidence paths other than `pre-handoff-check/`, ledger path, its angle, and the instruction to start from spec, diff and evidence before author reports, the self-audit and the implementer's pre-handoff check; no expected verdict or author reasoning. Each returns its findings in the review template's finding shape, about 600 words plus paths, without dropping findings; a longer list goes only to an assigned evidence path. Without suitable subagents, cover the angles directly and record that limit. After your own inspection, read the pre-handoff check and record its proposed ledger rows. Record verified findings in the review report and write its Pre-repair assessment checkpoint before any repair handoff. With no blocking findings, accept under Complete; otherwise hand a repair round to a fresh repairer under Repair.

Contained lane: the implementer's pre-handoff check is the review when the implementer closes under contract Review lanes (Implement). A forward review-and-fix session reviews the same way, directly or with read-only exploration subagents, reads the implementer's check only after its own inspection, then repairs under Repair.

Standalone review-only, only when Isaac asks: write the assigned report and a forward handoff to a fresh session assigned to act on it; no implementation, shared state, acceptance or delegation.

## Repair

Contained lane, reviewer-authored repair: the review-and-fix assignment already authorizes in-scope repairs and bookkeeping. Before writing code, preserve a dated, append-only pre-repair assessment checkpoint bound to the originally reviewed snapshot/session in the same review report. Record each finding as fixed, already satisfied, unsupported with counterevidence, accepted nonblocking deferral with reason, or unresolved blocker. Repair only supported in-scope issues and refresh affected checks, criteria and audit; do not rewrite correct code for taste. Keep original assessment intact. Record repair author, original/final snapshots, final spec revision, actual target/environment, inventory, changed paths, finding dispositions and final receipt in `Repair and final verification`. The reviewer-authored repair is never independently reviewed merely because the initial assessment was independent. Apply contract conditional closure: close when outcomes and evidence satisfy gates; a remaining material question that a fresh assessment can resolve goes forward as a focused review-and-fix assignment naming the question, scope and completion criterion, never back. Missing runtime/access/artifacts need their own proof. If neither check nor assessment resolves a material gap, leave pending/blocked with next action.

Four-session lane (rights and limits in contract Review lanes): for each round the reviewer-owner writes a repair handoff (Communicate) to a fresh repairer, transferring writing rights only and naming the supported findings, their required outcomes, the approved scope and affected checks. The repairer may contest a finding with evidence and never edits Status, dispositions or acceptance; it reruns the checks its changes affect until green, writes a repair report (the implementation-report template with the round in `cycle`, listing the findings addressed) and hands back to the current reviewer-owner, the only permitted return. The reviewer-owner gives each verification subagent the focused input below; read the repairer's round report directly, since `review-packet.py` binds to the Status implementation pointer. Record one round record in `Repair and final verification`, then close or hand another round to a new fresh writer.

Every focused verification or assessment assignment, in either lane, includes the original requirement/revision, finding ID and prior review, required outcome or dispute, repair delta, new snapshot and affected receipts. The author of repairs self-audits them across all eleven lenses against its final snapshot before closure or handback, reusing only unaffected earlier coverage with a stated basis: the contained reviewer after its last repair, in the review report's Post-repair self-audit; each four-session repairer for its round, in its round's self-audit report or, for a small repair, concisely in its repair report. Two unsuccessful rounds on the same issue trigger reassessment (a changed approach, the one STUCK diagnosis, or a decision for Isaac), not a third identical round or an automatic loop.

## Complete

Reconcile Implementation, Verification, Review and separate Integration/release. Accept only when criteria, required checks, initial fresh review, finding dispositions, repair closure for the lane (non-author verification, conditional closure, or confirmation checks) and project gates are satisfied. Do not relabel unmet requirements optional; explain nonblocking deferrals. Keep report provenance and original assessments. A contained implementer accepting after its pre-handoff check records its acceptance basis in the report and writes Status `Review: accepted (pre-handoff check, author-commissioned, no findings)`, `Review: accepted (pre-handoff check, author-commissioned, findings deferred: [IDs])` or `Review: accepted (pre-handoff check, author-repaired, repairs confirmed by a fresh subagent)`, with `; deferred: [IDs]` before the closing parenthesis for any deferrals. The accepting session holds task ownership: update ordinary Status or the established phase owner, ledger first occurrences including fixed defects and relevant lifecycle. Close or archive ledger rows with IDs/links intact; after 60 Closed rows move older rows to the ledger archive. Promote accepted permanent decisions to ADRs, verified setup facts to external records, and project conventions to their existing owner. An authorized writer may draft an already-accepted ADR or external record; the task owner reconciles it against the decision. Prefer project enforcement before a universal prompt rule. Verify applicable handoff and wrap updates, citing the Execution Receipt instead of copying logs. Do not turn uncertain lessons into settled rules. No task acceptance grants push, deploy, spending or production permission. End with either the next forward handoff, to the next slice's planner, or a completion summary.

## Resume

Resume means a fresh session continuing from the durable records; a session that has handed off never resumes the task. A session continued by mistake reads Status, finds that its task ownership or writing rights moved, and stops without writing. Compare actual tree, current Status or phase owner, relevant report Handoff, evidence and unresolved findings; do not choose solely by date or lifecycle. Reuse valid work and recheck changed inputs. Resolve an active/unknown prior writer; an ended writer can be reclaimed under existing authorized continuation after reconciliation. Preserve snapshot and unfinished work at transfer. At meaningful slice, risk, assistance, handoff or context pressure, update the current draft/evidence rather than inventing a tracker or approval. A rotating reviewer-owner (contract Session checkpoints and continuity) checkpoints open findings, what it verified and the pending round in its review report, then hands task ownership to a fresh reviewer-owner. Never invent context counts. After compaction reload uncertain protections, selected-reference requirements and procedures. If shared context exceeds roughly 3,000 words, promote details into focused docs with one index line per topic, preserve standing client-data/live-service/secret/production/approval protections in full, and log the promotion in spec log or maintenance record.

## Communicate

Lead with outcome, evidence and next action. Explain a material decision with the current rule, alternative, evidence, tradeoff and affected criteria. Keep technical details in records.

Every handoff ends the session's turn with one fenced copy-paste prompt of roughly 150 to 400 words that a fresh session can act on alone. It contains: (1) task, slice, spec path and revision, and the code snapshot; (2) the assignment (plan, implement, review as reviewer-owner, repair round N, review and fix, or resume), its authority and the lane; (3) the transfer line: which rights move (task ownership, writing rights or both), and that earlier sessions have ended and must not receive results; (4) five to ten factual lines on what happened, plus the current Implementation, Verification and Review states; (5) open findings, decision requests and approvals pending with Isaac; (6) records to open, in order; (7) the recommended host or model family, which for a reviewer-owner differs from the implementer's; (8) stop conditions and what to produce at the end: the next forward handoff, a repair handoff to a fresh writer, or a completion summary. Review handoffs carry facts and paths only, with no author justification or expected verdict; the author's reasoning stays in its report, which the reviewer reads after its own inspection. The durable records remain the source of truth; the prompt is only the entry point into them. The report's Handoff section records that a forward handoff was issued, and to which assignment.

Results move forward only. The one permitted return is a repairer handing back to the current reviewer-owner. Standalone review-only hands its report forward to a fresh session assigned to act on it; if it cannot write in the checkout, the handoff carries the exact report content so the receiving session preserves it with reviewer attribution. A subagent routes any assistance request through its parent; the parent handles the permitted user interaction. For bounded fresh subagent work, give its question, scope and stop condition directly; if a child tool is unavailable, use the documented direct or fresh-session fallback. Isaac performs every relay by pasting the prompt; there are no hooks, schedulers, runners, automatic handoffs or recursive loops. Do not ask Isaac to run terminal commands merely to move an ordinary workflow. Checkpoints, handoff, recommendation, acceptance and release remain distinct; do not ask again for work already authorized. State concrete blockers and the action that would resolve them.
